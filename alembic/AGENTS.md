## CONVENTIONS
- Additive-only, hand-reviewed migrations; the chain must apply cleanly on an empty DB. Dev/test DBs bootstrapped via `create_all` get `alembic stamp head` (they are not migrated).
- Hand-written, not autogenerated-in-place: 34 of 35 use bare `revision = "…"`; only 0000 keeps the Mako-emitted `revision: str = …`. Don't "normalise" either direction, and don't set `branch_labels`/`depends_on` — the chain is linear by construction.
- Every revision carries a docstring naming the ledger tag (W5 / P2-5 / OCR-A… / D-e2e-…), the paired `app/models/*.py` file, why an index is absent, and downgrade fidelity. 16/35 are fully Chinese — keep the mix.
- Boolean server defaults MUST use `sa.text("false")`/`sa.text("true")` (10 sites) — bare `"0"` is rejected by real PostgreSQL (D-e2e-08). 17 legacy bare `server_default="0"|"1"` sites survive in 6 older revisions: copy 0034, don't extend that pile.
- Types: `DateTime(timezone=True)` throughout, `server_default=sa.text("CURRENT_TIMESTAMP")`, PKs `postgresql.UUID(as_uuid=True)` from 0006 on (the baseline predates it with bare `sa.UUID()`).
- Composite index names in models (`ix_<table>_<cols>`) must match migration `create_index` names or `alembic check` reddens; the model layer is the other half of the parity contract.
- `env.py` contract: `sys.path.insert` then `import app.main` so `target_metadata` equals the `create_all` import set; online mode = `asyncio.run` over an async engine with `pool.NullPool`; `COMPARE_TYPES` parsed by `_parse_compare_types`.

## ANTI-PATTERNS
- Never edit alembic history (including the 0000 baseline) to add columns — new revision instead.
- **Revision-id width:** alembic's own version table is `VARCHAR(32)` and real PG16 blew up on the 0029→0030 stamp (34-char ids; SQLite never enforced it). Any id longer than 32 chars must sort AFTER the widen point 0030, and the `ALTER … VARCHAR(128)` must stay inside 0030 — `tests/test_alembic_version_id_width.py` pins both, including that the widen is PG-guarded.
- `ALEMBIC_COMPARE_TYPES=0` exists ONLY for the SQLite CI check (SQLite has no real types) — never use it to mask type drift on PostgreSQL. An unrecognized value raises `ValueError` (A217 fail-closed); never soften that parse back into "treat junk as off".
- Never drop the `%%` doubling in `config.set_main_option("sqlalchemy.url", …)` — real DSNs contain `%` (test_ocr_a211 pins the round-trip).
- Never remove `import app.main` from `env.py` — the parity gate compares against exactly that import surface.
- `scripts/verify_schema_parity.py` diffs table and column NAMES only. It cannot see type or index drift — those surface via `alembic check` and `deploy/e2e-remote/pg_validate.sh`. A green parity script is not a schema verdict.
- Never run `alembic upgrade` against production through `create_all` paths — prod forbids `create_all` (branch in `app/main.py`); prod requires Alembic + `verify_schema_parity.py`.

## COMMANDS
```bash
# Always the venv's alembic: the PATH-installed one runs system python and dies with a
# Protobuf gencode VersionError while importing app._stubs — a false failure, not a schema bug.
CDS_DATABASE_URL="sqlite+aiosqlite:///./ci.db" .venv/bin/python -m alembic upgrade head \
  && ALEMBIC_COMPARE_TYPES=0 .venv/bin/python -m alembic check       # SQLite CI shape
python scripts/verify_schema_parity.py                               # alembic vs create_all, exit 1 = CI fail
bash deploy/e2e-remote/pg_validate.sh                                # real PG16: head + create_all
CDS_DATABASE_URL=... .venv/bin/python -m alembic stamp head          # create_all-built dev/test DBs
```
